01 What This System Is

The Law Firm OS is the firm's AI operations layer — not a chatbot, but a small organization of specialized agents that run the back office of a law practice.

Each agent has a defined role, a fixed autonomy ceiling, and a single human in the loop: the Operations Manager, who is the primary interface to the system. The firm's attorney (President) and office administrator are the other human principals. The design goal is leverage without exposure: the agents draft, research, categorize, and surface — but they never send, never move money, never touch client files, and never act on their own outside a tightly bounded set of "autonomous" operations.

Practice

Criminal defense (primary) & personal injury, multi-county practice area.

System of record

Clio (client cases) — path-locked, never AI-accessible. The agents operate around it, never inside it.

Design principle

Draft & surface, don't execute. Every outward or irreversible action routes to a human for approval.

02 Org & Command Structure

The system mirrors a real executive team. Humans sit at the top; a single orchestrator agent — the Chief of Staff — is the only agent the operator talks to directly. Everything else is dispatched, verified, and synthesized back through that one point.

Operations Manager · President/Attorney · Office Administrator │ └── Chief of Staff [cos-001] ← the only agent the operator addresses directly │ ├── CFO [cfo-001] finance · billing · P&L · trust-accounting hygiene ├── CMO [cmo-001] marketing · SEO · web copy · reviews ├── COO [coo-001] ops · scheduling · deadlines · vendor comms │ └── can invoke → Research ├── Research [res-001] state criminal/PI law · statutes · agency rules └── Builder [bld-001] scripts · tools · dashboards · automations

The Chief of Staff never does domain work itself. It routes, enforces the rules, runs verification on every returned result, and hands the operator a single synthesized answer.

Agents read the four backbone files at every spawn before doing anything.

04 How Work Flows

A request from the operator always lands with the Chief of Staff, which decides the dispatch pattern:

Parallel

3+ unrelated tasks, no shared state, clean file boundaries. Fired concurrently.

Sequential

Any dependency, shared files, or unclear scope. Understood before proceeding.

Background

Research/analysis not blocking the current thread; results collected later.

Specialists return their work in a fixed report format. The Chief of Staff verifies it, redacts if needed, logs the outcome, and hands the operator one clean answer — never a transcript of the process.

Operator ──▶ Chief of Staff ──▶ dispatch ──▶ specialist(s) │ 5-field report ▼ Operator ◀── synthesized answer ◀── Verification (5 gates) ◀──┘

The report format — every agent, every time

TASK: what was assigned — one line STATUS: Complete · In Progress · Blocked · Needs Approval · On Hold · Failed SUMMARY: 2–3 sentences — what was done and the result FLAGS: what the operator must decide/approve/know — "None" if clean NEXT STEP: who does what next — "None" if complete

06 Privacy & Guardrails

This is a law firm: attorney–client privilege, HIPAA-adjacent medical records in PI cases, and state bar obligations all apply. The privacy protocol overrides every other instruction in every agent file.

Never accessed, under any circumstances: the protected client-files folder · the Clio folder · firm-member personal folders · anything referencing the co-counsel firm (cross-firm matter) — and every subfolder of these.
  • No client PII in any output — agents use "Client A", "the defendant", "Case #X".
  • PI files are treated as maximum sensitivity — never referenced, summarized, or processed.
  • Firm-member personal PII (tax docs, banking, medical, IDs) is off-limits, identical to client PII.
  • Drive search is path-discipline, not free-text — scoped to explicitly firm-public folders.
  • If unsure whether something holds PII, don't open it — flag to the Chief of Staff.

Enforced in code, not just in prose

Three runtime hooks turn the protocol into hard blocks at tool-call time — they fire before a tool runs and can deny it:

HookTriggerWhat it does
block_protected.shPreToolUseDenies any call touching protected/Clio paths — including Drive search query fields
scan_write_pii.shPreToolUseDenies writes containing SSN/DOB-shaped PII
memory_log_check.shStopEnforces MEMORY.md logging discipline at session end

Validated on day one, not in theory: the PII scrubber caught a real SSN-shaped string in a draft artifact, and the protected-path hook caught a shell command whose text contained the protected-folder token. Both denials were written to the audit trail. A standing precedent also bars agents from synthesizing PII even to test the detectors.

07 The Verification Gate

No output reaches the operator without passing all five gates. The Chief of Staff runs this on everything a specialist returns.

Gate 1
Scope — did the agent stay in its lane? Cross-domain drift is flagged.
Gate 2
Verification — did the agent check its own work? Self-reported "done" without proof is sent back.
Gate 3
Format — is it in the 5-field report format? Missing a field = rejected.
Gate 4
Privacy — any PII present? Redact before passing, and log the incident.
Gate 5
Completeness — any open items, blockers, partials? Surface them — never hide incomplete work.

08 Memory & Institutional Record

The system remembers. After every completed task the Chief of Staff appends one line to MEMORY.md in a fixed format — [date] [event] → [result/decision] — [agent/person] — and past entries are never edited, only appended. This is what lets a fresh session pick up context that isn't derivable from the code.

Standing decisions

Locked facts: the Clio path is immutable, the workspace is local-only, credentials live outside the repo, cross-firm access revoked.

Event log

A running history — audits, agent activations, verified statute lookups, architecture decisions — one line each.

Session close is ritualized through a /handoff command: reflect on the session, append the memory line, update WORKSPACE.md, and re-mirror to Drive.

09 Files, Hooks & Infrastructure

<workspace>/ ← local only, never Drive-synced ├── CLAUDE.md ABOS.md PROTOCOLS.md WORKSPACE.md MEMORY.md backbone ├── .claude/ │ ├── agents/ cos · research · coo · cfo (spawn definitions) │ ├── commands/ handoff.md (session-close ritual) │ └── hooks/ protocol enforcement + JSONL audit logger ├── agents/ SOUL / AGENTS / TOOLS / IDENTITY per agent ├── scripts/ config.py · mirror_to_drive.sh · hook_rollup.sh · drive/ ├── knowledge-base/ Firm Knowledge Summary · AI-Use Policy · security research ├── logs/hooks/ denials/ · actions/ · daily rollup/ ├── outputs/ agent-produced deliverables └── sop/ Agentic-BOS SOP + BUILD_LOG ~/.config/<firm>/ credentials (mode 600 — never moved or referenced in files) <runtime>/agents/ runtime agent files
  • Local-only workspace. The repo is never synced to Drive. A one-way, allowlist-driven rsync mirror exposes only firm-public docs — verified that .claude/, agents/, scripts/, and logs/ stay out of the mirror.
  • No credentials in any file. All auth lives in a mode-600 config directory; scripts import from config.py — no hardcoded secrets.
  • Audit trail. Every hook decision writes a JSON line to logs/hooks/; a daily job rolls it up to a markdown summary.
  • Workspace-scoped MCP. A filesystem MCP server scoped to the workspace, process-managed per session.
